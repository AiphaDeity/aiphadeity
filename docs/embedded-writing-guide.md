# AiphaDeity 嵌入式文章协作指南

本文件记录作者在 2026 年 11 月讨论后确定的写作方向与呈现要求。它是后续协作的工作依据，不代表候选文章已经写完，也不证明作者掌握了文中提及的所有技术。用户的新要求优先于本文件。

## 定位与分类

- 博客以嵌入式系统的学习、实践和知识整理为主线。面向初学者解释「是什么、为什么、怎样验证」，避免把单篇文章写成百科全书。
- 一篇文章只选一个主分类。分类表示文章的主要目标；标签表示正文实质涉及的芯片、外设、系统或工具。不要为每个型号和外设建立分类。
- 当前嵌入式文章采用四个分类：

| 分类 | 文章的主要目标 | 例子 |
| --- | --- | --- |
| 嵌入式基础 | 解释概念、系统结构和知识关系 | 通识、入门、寄存器原理 |
| 技术实践 | 围绕一个知识点或外设完成可复现的实验 | GPIO、UART、RTOS 任务实验 |
| 技术专题 | 深入研究一个具体技术问题、方案和取舍 | LVGL 移植、mbedTLS 集成 |
| 项目实践 | 围绕完整设备或功能目标记录设计、实现、验证和复盘 | 完整光照采集设备 |

- MCU、STM32、RTOS、Linux、寄存器、LVGL 等先作为标签使用。某方向积累足够多文章后，才考虑独立分类。
- 原「嵌入式通识」六篇编号系列规划已被后续讨论替代。现在的入口是两篇**独立文章**：《嵌入式通识：嵌入式到底是什么？》和《嵌入式入门：从哪里开始学？》。16 篇基础文章各自完整、标题不编号；为方便读者定位，使用 `series: 嵌入式基础阅读顺序` 和 `seriesOrder: 1～16` 提供推荐阅读顺序，不把顺序当作理解单篇文章的前提。

## 「嵌入式基础」的选题地图

下列选题既用于检查基础知识覆盖，也作为目前 16 篇文章的推荐阅读顺序。读者可以按需求跳读；后续如有内容调整，同步维护文章的 `seriesOrder` 和站内导航。

| 选题 | 核心问题 |
| --- | --- |
| 嵌入式通识：嵌入式到底是什么？ | 应用领域、系统行为、软硬件组成及常见概念的关系 |
| 嵌入式入门：从哪里开始学？ | 学习方向、基础准备和第一个可验证的实验 |
| 嵌入式开发需要懂哪些电路基础？ | 电压、电流、电平、供电、共地、上拉与下拉 |
| 从一颗芯片到一个能工作的系统 | 供电、时钟、复位、存储、引脚和外围电路 |
| CPU、存储器、总线与外设是什么关系？ | 程序执行及硬件各部分如何协作 |
| 设备怎样理解外界的信号？ | 数字量、模拟量、采样和控制输出 |
| 设备之间怎样交换数据？ | 接口、协议与数据格式的基本关系 |
| 写好的程序怎样在芯片上运行？ | 编译、链接、烧录和启动的整体过程 |
| Flash、RAM、栈和堆分别做什么？ | 程序与数据存放在哪里，资源为何受限 |
| 寄存器是什么？程序怎样控制硬件？ | 地址、读写、位操作和内存映射外设 |
| 设备怎样计时和响应事件？ | 轮询、定时器、中断和 DMA 的基本分工 |
| 裸机、RTOS 与嵌入式 Linux 怎样组织程序？ | 不同运行环境解决什么问题 |
| 实时性、功耗与可靠性为什么重要？ | 功能正确之外的设计约束 |
| 如何阅读芯片资料与开发板原理图？ | 数据手册、参考手册、勘误表和原理图各查什么 |
| 嵌入式问题怎样定位和验证？ | 从现象和假设到软硬件观察与验证 |
| 一个嵌入式项目怎样从需求走到交付？ | 需求、方案、实现、测试和复盘如何衔接 |

「嵌入式基础」只解释原理、关系和判断方法。具体寄存器配置、外设代码和 RTOS API 放在技术实践；围绕移植、集成和方案取舍的深入研究放在技术专题；真实完整项目放在项目实践。

## 写作要求

- 默认用中文。通常先确定本篇的读者、核心问题和边界；用户要求直接写正文时直接交付，不反复停在提纲。
- 以具体设备或现象引出问题，再解释概念和原因，最后回到例子说明如何验证。一段解决一个问题；段落和小节有清楚的推进关系。
- 标题与第一节标题不要重复。可以用编号的主要章节和少量小节建立层级；表格适合对照信息，流程图适合过程，组成图适合结构，时序图适合先后关系。不要机械地给每段配图或表格。
- 通识和入门篇通常约 3000～4500 汉字，概念篇约 2500～4000 汉字，方法篇约 2000～3500 汉字；这是编辑参考，阅读顺畅和内容完整优先于凑字数。
- 首次出现的必要术语解释中文含义和缩写。对常见情况使用「通常」「可能」等有边界的表述，不把 MCU、MPU、FPGA、CPU、操作系统、驱动库和开发工具混为同一层级。
- 区分事实、简化模型和建议。涉及特定型号行为、芯片参数、库支持或版本状态时，核对对应型号的数据手册、参考手册和官方文档，并写明适用条件。
- 不虚构作者的项目经历、技能熟练度或已完成的实验。未经亲自验证的内容写成教学示例或方案分析。
- Frontmatter 以 `src/content.config.ts` 的实际 schema 为准。文章先保持 `draft: true` 供审阅；未经用户明确授权，不发布、提交或推送。

## 图示与阅读呈现

- 图示的首要任务是解释关系。箭头应区分数据流、控制关系和时间顺序；简化图应说明省略了什么。光敏电阻示例不能漏掉分压电路、ADC，以及电脑通过 USB 接收时可能需要的接口适配；电机示例不能暗示普通芯片引脚可以直接供电驱动电机。
- 不为简单流程直接使用占满文章宽度和高度的 Mermaid 深色画布、缩放工具栏和细小节点。优先使用紧凑、主题感知、可在手机上阅读的 HTML/CSS 步骤图或对照卡；复杂关系确实需要 Mermaid 时，先检查实际渲染大小、空白比例和移动端效果。
- 图和表不能撑宽文章容器。窄屏表格在自身区域滚动；图示文字不能缩到难读。保留图下或图旁的文字解释，使不看图也能理解要点。
- 文章标题、章节标题、正文、摘要要有清楚的字号、字重和间距层级。深色阅读区使用对比清楚的中性表面，四季颜色用于少量点缀；避免大面积高饱和背景妨碍长文阅读。
- 引用块只保留一条左侧强调线和淡底色，避免全局伪元素与局部边框叠成双线。
- 当前 Markdown 处理链曾把紧贴中文的 `**加粗标记**后续文字` 输出为字面星号。加粗标记后加空格，或拆成独立段落；交稿前查看渲染后的页面，确认没有露出的 `**`。
- 对内容或阅读样式的修改，按仓库要求运行 `pnpm check`、`pnpm type-check`、`pnpm build`；涉及图示、表格和样式时，再用本地页面检查桌面与真实手机视口。说明实际检查结果，不把未验证的效果写成已完成。

## 第一篇的内容边界

《嵌入式通识：嵌入式到底是什么？》建立概念地图：跨行业应用、输入—处理—输出、硬件与软件、MCU／MPU／FPGA，以及运行环境与硬件访问方式的区别。它不展开寄存器字段、启动文件、任务调度、Linux 驱动模型或具体外设配置。输入—处理—输出是简化模型，不代表所有系统都是单向直线流程。第一篇草稿位于 `src/content/posts/embedded-introduction.md`。
