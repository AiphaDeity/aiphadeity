在电脑上写下让 LED 闪烁的代码，只是起点。芯片最终执行的是适合其处理器的机器指令，而且程序必须放在它会读取的位置。中间每一步都可能出错：代码能编译，不代表镜像能装入目标芯片；烧录成功，也不代表上电就会执行到主函数。

本文以常见的裸机 MCU 工程为例。使用引导加载程序、外部存储器或 Linux 的系统，步骤会有差异，但“代码怎样变成可启动的内容”这个问题始终存在。

## 一、源代码先变成目标文件

C 语言代码通常先经历预处理、编译和汇编，生成目标文件。预处理展开头文件和宏；编译器根据目标架构把代码转换为汇编或等价中间结果；汇编器生成机器代码。一个工程往往有多个源文件，每个文件产生的目标文件还不能独立代表整个程序。

编译器必须选择正确的目标架构、指令集和 ABI 等参数。电脑本机编译器产生的程序，不能直接假定可在 MCU 上执行。嵌入式工程常用交叉工具链，即在电脑上运行工具，生成给另一种处理器执行的代码。

若这一步报语法错误或找不到声明，问题多半在源文件、头文件或编译选项；此时还没到“烧录失败”的阶段。

## 二、链接把零散部分放到目标地址

链接器组合各个目标文件和库，解析函数与变量之间的引用，并确定代码和数据的布局。链接脚本常描述目标芯片有哪些存储区域，以及程序段放在哪里。对于某个具体 MCU，如果 Flash 和 RAM 地址、大小配置错误，程序可能无法正确装载或运行。

常见的只读代码、已初始化数据和未初始化数据会被放在不同区域。需要在 RAM 中运行的已初始化变量，其初值通常保存在非易失性存储器中，启动时复制到 RAM；未初始化变量所在区域通常由启动代码清零。具体段名与流程由工具链和启动代码决定。

链接成功后可能得到 ELF 等包含地址和符号信息的文件，也可以按烧录工具要求转换成 BIN、HEX 等镜像格式。文件格式不同，不等于程序逻辑不同；关键是镜像内容、地址和烧录方式要匹配。

## 三、烧录只解决“放进去”

烧录工具通过调试接口、系统引导程序或板载下载电路，把镜像写进目标存储器。写入后通常还会校验。这里需要确认三件事：选的是正确的芯片和接口，写入地址符合启动布局，烧录后有按预期复位或重新上电。

“烧录成功”只说明指定内容被写入和校验，并不证明外部电路、启动选择或程序行为正确。若有引导加载程序，还要区分引导程序的入口地址与应用镜像的地址；不能把任意二进制文件写到任意位置。

## 四、复位后不是直接进入主函数

芯片复位后，处理器先依据架构和芯片的启动规则取得初始状态与入口地址。在常见 Cortex-M 工程中，向量表包含初始栈指针和复位处理程序地址。复位处理程序通常进行必要的运行时初始化，再调用主函数。不同架构和工具链的细节并不完全相同。

如果程序还没进入主函数，可能是启动配置、向量表、链接地址、栈指针、系统时钟初始化或外部电源等条件有问题。用调试器在复位处理程序和主函数设置断点，常能迅速确认停在链路的哪一步。

## 五、用证据区分每一阶段的问题

可以沿着下面的顺序观察，而不是只问“为什么灯没亮”：

1. 编译日志是否无错误，目标架构是否正确？
2. 链接映射文件中，代码、数据、栈等是否落在预期存储区域？
3. 烧录工具是否报告了正确设备、地址和校验结果？
4. 复位后调试器是否能停在启动入口与主函数？
5. 程序进入主循环后，引脚配置和外部 LED 电路是否正确？

每一步只说明其自身成立，不自动证明下一步。这样排查会比重复点击“重新构建并下载”更有效。

## 六、别把不同文件当成同一件事

初学者常同时看到源文件、目标文件、ELF、HEX 和 BIN，不知道该把哪个交给烧录工具。源文件是人编写的代码；目标文件是单个编译单元的结果；ELF 通常包含多个段、符号与地址信息，适合调试和分析；BIN 通常是一段原始字节，没有自行描述“应该写到哪里”的信息；HEX 等格式则可以携带地址记录。实际交付哪种格式，取决于烧录工具与启动方案。

因此，“把 BIN 文件拖进工具”时，工具界面若还要求填写起始地址，这个地址不是可以猜的。要从链接配置、芯片存储布局和引导方案中确认。若有应用偏移、双镜像更新或安全启动，地址关系会更复杂。

也要区分烧录器、调试器和串口工具。板载调试器可能同时提供下载接口与虚拟串口，但这两条功能链并不相同。串口终端能打开，不证明调试口一定连通；固件能下载，也不证明程序的 UART 初始化正确。

## 七、一个可重复的构建记录

若同一份源码在两台电脑构建出不同行为，应记录工具链版本、构建选项、目标芯片型号、链接脚本、启动文件和所用依赖。程序大小、入口地址和关键段位置也可从构建产物中检查。

对教学实验，可以在每次下载后先观察一个明确的“版本标识”，例如串口输出构建版本或让状态灯按版本特征闪烁。这样能排除“实际运行的还是旧固件”这一常见误判。对于正式产品，版本信息和更新策略还应纳入交付。

如果一段代码已经能运行，后来修改后无法启动，最有价值的是比较本次与上次在构建和启动链路上的差异，而不是立即更换开发板。

## 八、看懂“编译通过却运行不了”的几种情况

假设工程从一块芯片移到同系列另一型号，代码能编译、链接也成功，下载后却停在异常处理程序。第一步是核对目标型号和启动文件：向量表中断入口、存储大小、外设地址可能并不完全相同。再看链接脚本里的 Flash 与 RAM 起始地址、长度是否对应新型号。代码能被编译器翻译，只说明语法和目标指令选择没有阻止生成文件，不保证这些地址与实际硬件相符。

另一个常见情况是程序更新后仍看到旧行为。可能烧录到错误的设备，也可能工具只下载了部分镜像，或复位后实际从另一启动区域执行。此时在构建产物中写入可识别的版本号，烧录后读回或通过调试器检查存储内容，比反复修改 LED 闪烁周期更容易证实运行的是哪一版。

还有一种问题发生在主函数之前：启动代码需要把已初始化数据的初值从镜像位置复制到 RAM，并清零约定的数据区。若链接脚本的装载地址与运行地址配置不一致，变量在主函数开始时就可能是错的。并不是所有异常都能靠“主函数里加日志”看到，必要时应从复位入口逐步观察。

## 九、区分程序入口与业务入口

初学者常把主函数当成处理器上电后的第一条指令。对常见 Cortex-M 裸机工程，处理器按向量表信息获得初始栈指针与复位处理程序入口；复位处理程序完成运行环境初始化后才进入主函数。若使用引导加载程序，可能先执行另一段程序，再跳转到应用；某些系统还要验证固件镜像或选择启动槽位。

这条链也说明为什么“烧录地址”和“链接地址”必须一致。引导加载程序把应用放在 Flash 的偏移位置时，应用向量表和中断入口要与该布局匹配。它不是把原本从地址零启动的二进制文件随意向后移动就能可靠工作。

实际项目可把构建命令、链接映射文件、镜像格式、烧录命令与目标板版本记录在一起。一个能够重复生成并下载的工程，比只保留 IDE 中某次成功运行的配置更适合交付和排查。

## 小结

源代码经编译、链接成为有目标地址的程序，再由烧录工具写入存储器；复位后的启动代码把运行环境准备好，应用代码才开始执行。搞清这条链路，就能把“程序没跑”拆成几个可检查的问题。
