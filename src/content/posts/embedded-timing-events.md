设备要每隔一段时间采样，还要及时响应按键。最直接的写法是不断检查时间和引脚状态；需求变多后，就会遇到“忙着做一件事时，另一件事怎么办”的问题。轮询、定时器、中断和 DMA 是处理这类问题的不同工具，彼此可以组合，不是一条由低级到高级的升级路线。

## 一、轮询：程序主动去看

轮询是在程序循环中检查条件。例如反复读取按键电平，发现状态变化后执行动作。它简单、可控，事件数量少且允许一定响应延迟时很有用。

问题在于检查要花 CPU 时间。循环里若有很长的阻塞等待，就可能错过短暂事件；若为了响应更快而不停查询，也可能增加功耗。轮询周期与事件持续时间要匹配，不能只凭“循环很快”保证不会漏。

按键还会抖动。无论轮询还是中断，都需要决定怎样把一次机械按压转换为一次有效事件；换成中断并不会自动消抖。

## 二、定时器：让硬件帮助数时间

软件可以根据时钟做延时，但 CPU 若一直空转等待，就不能有效处理其他工作。定时器是专门计数的外设，可按配置产生周期事件、比较匹配、输入捕获或 PWM 等功能，具体能力取决于芯片。

例如，每隔固定周期读取一次传感器，可以让定时器产生节拍，然后由程序轮询标志或处理中断。计算采样间隔时，要知道定时器实际时钟、分频与计数范围；“CPU 主频是多少”不一定就是该定时器的计数频率。

定时器有精度和范围，也会受时钟源误差影响。若要求长期准确的日历时间，普通定时器与实时时钟、外部时间同步解决的问题并不一样。

## 三、中断：事件发生时通知 CPU

中断允许某些事件在发生时请求 CPU 暂停当前执行流程，转而运行对应的处理代码，完成后再继续原流程。按键边沿、串口接收或定时器到期都可能成为中断来源。

中断能减少反复查询，但不能保证“事件一发生，处理代码立刻执行”。中断屏蔽、优先级、其他处理程序和 CPU 当前状态都会影响响应时间。中断处理还应尽量短，常见做法是在中断中记录必要状态，再让主循环或任务完成耗时工作。

中断也带来共享数据问题：主循环和处理程序可能先后访问同一变量。需要考虑可见性、原子性和同步，不能仅凭一个变量声明就推断所有竞争都解决了。

## 四、DMA：搬运数据时少让 CPU 逐字节参与

DMA 通常指直接内存访问机制。芯片中的 DMA 控制器可在配置后，于外设与存储器或存储器之间搬运数据，减少 CPU 对每个数据单元的参与。例如串口连续接收一段数据时，DMA 可把数据放进缓冲区，再通知 CPU 处理。

DMA 并不会理解数据含义，也不负责自动处理所有边界问题。CPU 仍要配置传输源、目标、长度和触发条件，并管理缓冲区何时可读写。带缓存的系统还可能需要处理缓存一致性。使用 DMA 也不一定更快：小数据量、低频事件时，配置成本和复杂度可能不划算。

## 五、把四者组合进一个任务

设想设备每隔一段时间采样，并允许按键切换显示模式。一种简单实现是主循环轮询按键，用定时器标志控制采样。若采样频繁、数据量增大，可考虑定时器触发采样并让 DMA 收集结果；按键中断只记录变化，再由主流程消抖并更新状态。

这个例子不指定唯一最佳方案。选择依据是事件频率、最迟响应时间、CPU 负载、功耗和实现复杂度。先写出“允许多晚响应、每次搬多少数据、能否丢一次事件”，才知道需要哪种机制。

## 六、先写清楚时间指标

例如“按键要及时响应”，可以细化为：从稳定按下到界面变化，允许的最大延迟是多少？按键抖动时间算不算？系统同时在发送数据时，要求是否仍成立？有了边界，才能决定轮询间隔或中断处理策略。

周期采样也要区分“每隔固定时间启动一次采样”和“上一次处理结束后再等待固定时间”。前者更接近固定节拍，后者会把处理耗时累加进周期。若采样结果要求准确的时间戳，就要确认时间戳记录发生在触发、转换完成还是软件处理时。

## 七、常见误区是把通知当成处理完成

定时器产生中断，说明计时事件发生；不说明采样、计算、通信都已完成。DMA 传输完成，说明缓冲区搬运达到配置条件；不说明缓冲区内容已被应用正确解析。中断通知任务，也不说明任务马上获得 CPU。

可以为每个阶段设置可观察点：事件触发、处理开始、处理结束、输出生效。用逻辑分析仪或示波器观察 GPIO 标记脉冲时，脉冲会稍微改变执行时间，因此测量方法也要记录。比较最忙时的延迟，比只看空闲状态更接近实际要求。

如果发现超时，先定位时间花在哪一段。可能是轮询周期太长，也可能是某段代码阻塞、锁竞争、外设等待或低功耗唤醒耗时。只有把延迟拆开，才能判断该改调度方式、外设配置还是需求本身。

## 八、算一个轮询是否足够的例子

假设程序每 10 毫秒读取一次按键，而按键按下后通常保持几百毫秒。若主循环没有长时间阻塞，这样的检查节奏一般有机会观察到状态；若它同时在某一步等待通信 500 毫秒，按键又在等待期间按下并松开，轮询可能完全看不到。问题不在“10 毫秒是否先进”，而在实际最坏检查间隔是否满足事件持续时间和响应要求。

同样的逻辑用于采样传感器：若需要每 100 毫秒得到一次结果，不能只在循环末尾延时 100 毫秒，因为采样和处理本身也耗时。应明确周期从哪个时刻算起，并观察连续多次的实际间隔。定时器可提供更稳定的触发点，但转换完成和软件处理仍可能在后面发生。

## 九、中断和 DMA 也有边界

中断到来时，CPU 会先处理当前不可中断的片段，再按优先级与系统规则进入处理程序。若处理程序里打印大量日志、等待锁或执行复杂解析，其他事件的响应可能被拖慢。较稳妥的结构是只保存必要状态、清除相应硬件标志，再把后续工作交给主循环或任务；具体清标志顺序要查手册。

DMA 可减少逐字节搬运的 CPU 指令，但缓冲区长度、循环模式、半传输与完成事件都需要设计。若接收端不断写入同一缓冲区，而处理程序还在读取旧数据，就会读到混合内容；若存储器有缓存，还可能读到未同步的数据。使用 DMA 的理由应是可测的吞吐量或 CPU 负载需求，而不是它看起来更“高级”。

一个方案可以把四者结合：定时器定期触发 ADC，DMA 把结果放入缓冲区，完成中断只通知应用，主循环或任务做滤波和发送。这个简化流程仍需核对具体芯片是否支持相应触发链路、缓冲区是否足够，以及最坏处理时间是否短于下一批数据到来间隔。

## 十、把时间指标写成可测量点

如果要求“按下后 30 毫秒内灯亮”，应明确起点是机械触点第一次闭合、稳定闭合，还是软件确认按下；终点是 GPIO 寄存器写入、引脚电平改变，还是 LED 实际发光。不同定义的测量结果不可直接比较。对有消抖的系统，稳定确认本身通常需要时间。

然后在最忙的工作场景下测多次，记录最大观察值与测试条件。若总延迟不满足要求，再把它拆成输入检测、中断或轮询等待、任务调度、计算与输出几段。只有知道主要耗时在哪，才能有针对性地修改设计。

计时器的计数范围也有限，运行到上限后可能回绕。如果程序用“当前计数值必须大于上次计数值”判断时间前进，长时间运行后可能突然失效。常见做法是按计数器位宽和无符号差值计算经过时间，但具体实现必须保证比较的时间间隔不超过算法允许的范围。对长期运行的设备，回绕不是罕见边界，而是迟早会发生的正常情况。

## 小结

轮询负责主动检查，定时器提供硬件时间基准，中断负责事件通知，DMA 帮助搬运数据。它们都服务于具体时序要求。评估一种设计，关键不是用了多少外设，而是能否在可验证的时间与资源边界内完成工作。
