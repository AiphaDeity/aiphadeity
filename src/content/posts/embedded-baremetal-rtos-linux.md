一台设备要读取传感器、更新屏幕、响应按键并上传数据。它不一定需要操作系统，也不一定能靠一个无限循环长期维持清晰结构。裸机、RTOS 和嵌入式 Linux 提供了不同的程序组织方式；选哪一种，取决于任务、硬件资源和维护要求。

这里讨论运行环境如何安排工作，而不是按“低级、中级、高级”给技术路线排名。一个设计良好的裸机系统可以很可靠；一个使用 Linux 的系统也可能因时序设计不当而错过截止时间。

## 一、裸机：程序直接安排主要流程

“裸机”通常指不依赖通用或实时操作系统内核，由应用代码和必要的驱动直接管理硬件。最简单的结构是初始化后进入主循环：轮流读取输入、更新状态并控制输出。中断和定时器仍然可以使用；裸机不等于“只能写死循环”。

任务少、时序关系清楚、资源有限时，这种方式易于理解和控制。但若在某一步长时间阻塞，其他工作可能得不到及时处理。项目变复杂后，开发者需要自己明确事件队列、状态机、优先级和共享数据规则。

裸机代码可以使用芯片厂商的硬件抽象库。库是访问硬件的软件接口，并不会因此变成操作系统。

## 二、RTOS：把工作拆成受调度的任务

实时操作系统内核通常提供任务调度、定时、任务间通信和同步等机制。应用可把采样、通信、界面等工作分成任务；内核根据配置的调度规则决定谁运行。每个任务通常需要自己的栈，队列、互斥量等对象也占用 RAM。

RTOS 的“实时”强调对时间要求的可分析和可满足，不是“任何代码都自动更快”。高优先级任务若长期占用 CPU，低优先级任务会饥饿；互斥资源处理不当会导致死锁或优先级反转。把所有工作都塞进多个任务，也可能比一个清晰的状态机更难维护。

中断仍然存在。常见结构是中断快速记录事件，再唤醒任务做耗时处理。具体哪些 API 可在中断中使用，必须查所用 RTOS 的文档。

## 三、嵌入式 Linux：完整的系统软件环境

嵌入式 Linux 通常运行在具备相应处理能力和内存管理条件的平台上，提供进程、文件系统、网络栈和大量驱动框架。应用可以在用户空间开发，利用成熟的系统接口；需要直接控制特殊硬件时，可能涉及设备树、内核驱动或现有子系统。

这带来生态和功能优势，也增加启动、存储、内存、系统更新和安全维护的成本。Linux 系统不是“把 MCU 程序换个编译器”就能迁移过去。进程隔离、内核与用户空间边界、文件系统和驱动模型都会改变开发方式。

Linux 也能用于有时间约束的场景，但是否满足具体截止时间，要看内核配置、驱动、硬件和实测的最坏延迟。不能因为“跑了 Linux”就判断不实时，也不能因为“装了实时补丁”就假定所有响应都可保证。

## 四、用需求决定结构

假设一个节点只需定期采样、亮灯并低频发送数据，资源小且逻辑简单，裸机可能足够。若它还要同时处理通信、多个控制周期和复杂状态，RTOS 的任务与同步机制可能有帮助。若它需要成熟的图形界面、复杂网络服务和文件管理，并有合适硬件，嵌入式 Linux 可能更合适。

选择前先写明：需要同时处理哪些工作？允许的响应延迟是多少？可用 RAM 与存储有多少？启动时间、功耗、更新和维护有什么要求？这些问题比“大家都在用什么”更有决定性。

## 五、三种环境下同一个需求如何落地

假设设备每秒读取一次传感器，按键可以改变显示页面，同时后台要发送数据。裸机方案可以让定时器标记采样到期，主循环依次处理采样、按键状态和发送队列；关键是每一步都不长时间阻塞，且状态变化清楚。RTOS 方案可把采样与通信分成任务，用队列传递数据，界面任务根据消息更新；关键是任务栈、优先级和共享资源设计。Linux 方案可能把采样与界面做成进程或服务，通过已有驱动和系统接口获取数据；关键是用户空间和内核接口、服务管理及异常恢复。

三种设计都能完成同一功能，结构却不同。不能直接把裸机循环中的“等待 1 秒”照搬到高优先级 RTOS 任务，也不能把 Linux 用户进程当作可直接访问任意物理寄存器的裸机程序。迁移时要重看并发、时间和硬件访问边界。

## 六、评估复杂性是否值得

RTOS 和 Linux 提供了现成机制，却也要求理解新的约束。多任务系统中的共享状态可能发生竞争；任务优先级设置不当会让表面上独立的功能互相阻塞。Linux 还需要考虑启动链、文件系统掉电、系统更新和长期维护。另一方面，自己在裸机里实现大量任务调度、网络和文件管理，也可能比引入成熟系统更难验证。

一个实用判断方法是先列出必须使用的系统能力，再列出对应硬件资源。若只有两个周期任务和一只按键，先用简单结构做出可测原型；若需要复杂网络、图形和存储服务，再评估操作系统带来的收益。方案选择应随真实需求变化，而不是把早期技术选型当成永久身份。

## 七、RTOS 的“多任务”到底怎样运行

在单核 MCU 上，多个任务通常不是同一瞬间都在执行。调度器选择一个就绪任务运行；任务等待队列、定时器或外设事件时可以阻塞，让其他任务获得 CPU。以常见的固定优先级抢占式调度为例，高优先级任务一旦就绪，可能抢占正在运行的低优先级任务。具体策略和配置要看所用 RTOS；不能把某个内核的默认行为当作全部 RTOS 的规则。

设想采样任务每隔一秒取数，通信任务等待新数据。采样完成后把一条消息放进队列，通信任务醒来发送。队列让两个任务交换数据，但它也有容量：如果产生速度长期高于发送速度，队列最终会满。此时应决定丢弃、覆盖、回压还是报警，而不是以为“用了队列就不会丢数据”。

任务优先级同样不能只按功能名称设置。“通信重要”不说明它必须始终高于采样；若它在等待网络时持续占用 CPU，其他功能可能无法及时运行。先写出每项工作的截止时间、最长运行时间和等待条件，再配置任务与优先级。

## 八、Linux 应用为什么不能照搬裸机写法

在 Linux 上，普通应用运行在用户空间，访问设备一般经内核提供的文件、字符设备、网络接口或其他系统 API。应用不应假设自己能像裸机那样直接对任意物理地址写寄存器。设备树和驱动描述或管理硬件，是另一层工作；若已有合适驱动，应先使用它提供的接口。

例如同样读取一个温度传感器，裸机程序可能直接配置 I²C 控制器和传感器寄存器；Linux 应用通常先确认内核识别了总线和设备，再通过相应驱动接口取数。这样能复用系统的设备管理能力，也意味着调试时要分清“传感器没响应”“内核驱动没绑定”和“用户程序解析错了”。

文件系统和进程管理使日志、配置与软件更新更方便，但也带来掉电一致性、启动服务顺序与权限问题。设备若在断电频繁的环境中工作，不能只因为 Linux 有文件系统就随意写配置文件；还要设计原子更新和异常恢复方式。

## 九、用一张选择清单收束

做技术选择前，回答五个问题：任务是否需要可证明的响应上限？系统有多少 RAM 和非易失性存储？是否需要现成网络、图形和文件系统？允许多长启动时间与多少待机电流？团队能否长期维护该运行环境？

如果这些问题尚无答案，先做最小原型并测量。选择运行环境不是表态，而是选择谁来承担调度、资源管理和系统服务，并为这些能力支付资源与维护成本。

## 小结

裸机让应用自行组织主要流程；RTOS 提供调度与任务协作；嵌入式 Linux 提供完整的进程和系统服务。它们都能做嵌入式系统，差别在于谁管理复杂性、付出多少资源以及如何验证时间与可靠性要求。
